Trigger overrides let you to modify the default behavior of specific aspects of a workflow trigger (event), giving you fine-tuned control over how messages are delivered across different channels and providers.

## Channel overrides

Channel overrides let you customize specific channel settings and content during workflow trigger. Each channel has its own supported override options, documented in their respective channel guides.

<Note>
  Channel overrides is only available for Email and SMS channels.
</Note>

## Provider overrides

Provider overrides give you fine-tuned control over how messages are delivered by allowing direct configuration of the underlying provider SDKs during the workflow's trigger phase.

This feature is designed for advanced use cases where Novu's default message editor or UI does not expose specific provider capabilities.

Use provider overrides to:
- Access native provider features not surfaced by Novu’s abstraction layer. For example, custom headers in SendGrid, topic messaging in FCM, or [Slack Block Kit](/platform/integrations/chat/slack#format-messages-with-block-kit).
- Adapt to provider-specific options by injecting parameters that Novu doesn’t yet officially support.
- Configure shared or unique settings across steps without altering templates or workflow logic.

This mechanism offers a flexible customization layer that lets you pass deeply nested payloads that align directly with your provider’s native API. It helps decouple workflow behavior from provider-specific implementation details, which is essential when working across multiple channels like email, push, or chat.

<Note>
  Because overrides interact directly with provider SDKs, they won’t work if they're misconfigured. Make sure you understand the supported options for each provider before using this feature. 
</Note>

### Provider override scopes

Overrides are defined in the `overrides` property of a trigger payload. You can specify configuration values at two levels:
- Workflow-level: Applies to all steps using a specific provider and takes precedence over the default workflow provider settings.
- Step-level: Targets a specific step in the workflow and it takes precedence over both workflow-level overrides and the default workflow provider settings.

At either level, you can key an override by provider ID, such as `slack`, or by integration identifier, such as `slack-eng`. Integration keys target one integration when several share a provider, and they take precedence over provider keys. See [Target a specific integration](#target-a-specific-integration).

Some channels also let you save provider overrides on the step itself in the workflow editor, rather than sending them with every trigger. Those configured overrides sit below both scopes above: anything you send at trigger time replaces the configured value for the same field, and fields you do not send keep their configured values. See [chat provider content overrides](/platform/integrations/chat#provider-content-overrides).

<Warning>
  **Arrays replace, they do not merge.** When an array key is set at more than one level, the higher-priority array is used whole rather than merged element by element. Previously arrays were merged by index, which could leave a partial array patched over a longer one. Send the complete array at the level you want to win.
</Warning>

### Workflow-level provider overrides

Workflow-level provider overrides apply configuration to all steps that use a given provider in the workflow. They’re useful for applying shared logic across multiple steps, without repeating the same settings in each one.

Use workflow-level overrides when:
- You need to define common metadata like headers, personalization, or layout settings.
- You want consistent behavior across all steps for a given provider.

#### Sending extra fields supported by provider SDK

You can also send extra fields supported by the provider SDK. For example, if you want to send a headers to the provider SDK, then you could use the `_passthrough` field.

```json
"overrides": {
  "providers" : {
    "sendgrid": {
      "_passthrough": {
        "headers": {
          "Authorization": "Bearer my-api-key"
        }
      }
    },
  },
},
```

### Step-level overrides

Step-level overrides let you apply provider-specific settings directly to an individual step in your workflow.

Use step-level overrides when:
- You want to send push notifications through the same provider, but with different settings for each step. For example, two steps use FCM, but each sends a different sound or title.
- You need to customize the payload for a specific push step, such as platform-specific settings for Android and iOS, without affecting other steps.

### Target a specific integration

A provider key applies to every integration of that provider. When an environment has several integrations of the same provider, key the override by integration identifier instead, so each integration receives its own payload.

Use integration-keyed overrides when:
- A chat step sends through two integrations of the same provider, such as two Slack integrations for different workspaces, and each needs different content.
- [Integration conditions](/platform/integrations/integration-conditions) route a step to one of several integrations of the same provider, and each needs different settings, such as a different email `from` address.

Integration keys are available at two levels:
- `overrides.integrations.<identifier>`: Applies to every step that sends through that integration.
- `overrides.steps.<step-id>.integrations.<identifier>`: Applies only to that step when it sends through that integration.

In this example, the workflow has a chat step that sends through two Slack integrations, `slack-eng` and `slack-sales`:

#### Override precedence

When more than one level sets the same field, Novu applies them from lowest to highest priority, and the later level wins:

1. Overrides saved on the step in the workflow editor, or set in the step's [`providers`](/framework/typescript/steps#providers-overrides-object) option in a Framework workflow. These are keyed by provider.
2. `overrides.providers.<provider-id>`
3. `overrides.steps.<step-id>.providers.<provider-id>`
4. `overrides.integrations.<identifier>`
5. `overrides.steps.<step-id>.integrations.<identifier>`

Integration keys win over every provider key, including step-level provider keys. Merging works the same way at every level: objects merge deeply, arrays replace whole, and `null` clears a value set at a lower level. Triggers that only use provider keys behave as before.

#### Integration identifiers

- Each integration's identifier is shown on the integration in the **Integration Store**. See [Provider vs. Integration](/platform/integrations#provider-vs-integration).
- Identifiers are unique within an [environment](/platform/developer/environments), and each environment has its own integrations. Make sure the key you send exists in every environment you trigger from.
- Keys must match the identifier exactly. If an integration's identifier changes, the old key stops matching.
- Novu ignores keys that don't match an integration the step sends through. The trigger doesn't fail.

#### Supported steps and limitations

Integration keys work on chat, email, SMS, push, and Tool steps, such as [Tool Webhook](/platform/integrations/tool/webhook). For email steps, they can also set `cc`, `bcc`, `from`, and `replyTo`, the same way provider keys do.

- In-app (Inbox) steps don't support integration keys.
- Overrides saved on a step in the workflow editor are keyed by provider only. You can't save per-integration overrides in the dashboard yet, so send them at trigger time.
- Push overrides that add a delivery target at trigger time, such as FCM `tokens` or `topic` for a subscriber without stored device tokens, are only read from provider keys. Send them under `overrides.providers.<provider-id>` or `overrides.steps.<step-id>.providers.<provider-id>`.

### Slack Block Kit overrides

Use trigger overrides to send [Slack Block Kit](https://api.slack.com/block-kit) messages that only your calling code can build. Pass a `blocks` array under `overrides.steps.<step-id>.providers.slack`, or use `_passthrough.body` for raw Slack API fields.

<Note>
  You can also save Slack overrides directly on the Chat step in the workflow editor, which keeps the layout versioned with the workflow instead of duplicated across every trigger call. That editor is [rolling out gradually](/platform/integrations/chat#provider-content-overrides). Use trigger overrides when the message depends on data your application only has at send time.
</Note>
